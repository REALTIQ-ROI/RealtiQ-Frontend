## A. Executive summary

Chapter 16 contains **45 variation-matrix rows** mentioning **44 unique mounted path patterns**. It separately lists **three cross-cutting contract additions** (protected payment CSV, saved-search revisions, and unit-grid undo metadata). ## D–E. Success, pending and partial outcomes

- Tour request creation consumes `{tour}`; tour listing consumes a bare array and response headers; tour status update consumes a bare DTO. The frontend does not normalize these into one generic envelope.
- Payment/escrow 202 responses remain pending. Escrow detail refreshes; proxy payment initialization retains its reference and waits for the payment-verification endpoint. Provider redirects are not treated as payment proof.
- Refund processing 202 remains processing; cancellation is not mapped to refund completion. The wallet is a ledger projection, not a settled-bank balance.
- Proxy price confirmation state is driven by returned request flags. Completion submission, buyer confirmation, payout, and provider settlement are separate states.
- Private-file migration/custody 202s are not consumed by the user-facing frontend; there is no frontend UI that could imply completion.
- Empty arrays and zero totals are rendered as successful empty results in tour, wallet, escrow, and proxy list flows.

## F–G. Error envelopes, conflicts, retries

- `normalizeApiError` handles documented `{message,code}` and `{code,errors:[...]}` forms, nested field paths, request ID, retry-after, and documented fields such as payment reference, pending status, reconciliation requirement and completion `missing[]`.
- 401 dispatches session-expiry cleanup; 403 is permission denial and does not log out. 409 is not automatically retried; supported UI refreshes the authoritative record.
- This pass added `existingRequestId` to `ApiRequestError` and parses that documented top-level field. A race-time duplicate request can now open the existing request rather than leaving the user with an unlinked error.
- Rate limits preserve `Retry-After`; no automatic generic retry is scheduled. 503 `FEATURE_PAID_TOUR_UNAVAILABLE` is presented as product/capability unavailable, not a transient outage.
- 11 consumer rows remain PARTIAL only because their specific branch lacks a dedicated mock assertion. Their service/UI behavior was source-traced; no known incorrect recovery or automatic retry was found.

## H–I. Authentication, authorization and protected operations

- Shared Axios context continues to send bearer and selected-profile headers. Its 401/403 distinction and validation-path preservation have focused tests.
- Protected proxy payment initialization, price confirmation and Admin financial actions retain one-use body/path-bound step-up. No challenge is persisted or replayed after mutation failure.
- Chapter 16’s Admin proxy family requires step-up. Chapter 07 gives exact bodies for inspector review (`decision` plus notes/reason), suspension (`reason`) and reactivation (`notes`). Those previously disabled controls now use `useBoundStepUp`, submit `X-Step-Up-Challenge` from the verified challenge, preserve the exact JSON body, refresh only after server success, and cancel on route/profile change.
- Proxy evidence signed URLs are validated and treated as short-lived private content. They are not stored in persistent browser state.
- No access to private migration/custody endpoints was added to the first-batch UI; Chapter 14 classifies these paths operational/internal and Chapter 13 describes them as operations-console workflows gated by policy/storage readiness.
