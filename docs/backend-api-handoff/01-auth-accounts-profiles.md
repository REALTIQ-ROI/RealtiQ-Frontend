# Auth, accounts, profiles and permissions

## Legacy identity routes (compatibility; prefer profile APIs)

The following paths are mounted under `/api/users` in `src/routes/userRoutes.js`:

| Endpoint | Contract |
|---|---|
| `GET /api/users/:id` | Self receives the authenticated-user projection; current admin with staff-route permission receives a staff projection; another caller may receive only a public seller profile for a landlord account. Otherwise 403/404. |
| `PATCH /api/users/:id` | Bearer auth + step-up. Body keys only `name`, `phone`, `profileVisibility`, `accountStatus`, `expectedAuthVersion`. Name is 1–120 chars and contact-guarded; phone must be E.164; visibility `private|public`; account state `active|suspended|blacklisted`; version is a non-negative integer. Self may change identity/settings, but profile visibility is redirected to current-profile privacy workflow. Account-state/admin actions require current staff permission; suspension/blacklist/deletion require Executive and exclude Internal Audit. Identity changes revoke sessions and invalidate identity-bound verification approvals. |
| `DELETE /api/users/:id` | Admin route + step-up; body permits only optional `expectedAuthVersion`. The service requires current Executive department and resource permission. This is an account-deletion state transition, not hard deletion; response `{message,id}`. Prefer the data-protection deletion request flow for data-rights requests. |
| `GET /api/users`, `GET /api/users/landlords` | Admin plus current staff route permission; response is staff-user projection or public seller-card list. These are legacy operator directory paths; use profile APIs for user-facing profile screens. |

Legacy `/api/verification/submit` and `/api/verification/review/:userId` routes do not implement current profile verification cases; they reject with `409 CONFLICT_KYC_PROFILE_WORKFLOW_REQUIRED`. Use `/api/profiles/current/verification-cases` and the current admin verification queues.

All profile APIs mount under `/api/profiles`; the router applies Bearer auth, Registered access, private/no-store headers, and current active-profile resolution. `X-Profile-ID` selects an authorized workspace. Omission uses the identity's current primary profile where supported. The identity token is not a company membership grant.

## Authentication/session endpoints

| Endpoint | Request | Success response | Notes/errors |
|---|---|---|---|
| `POST /api/auth/register` | JSON fields validated by `authValidators`; standard registration includes name/email/password/role. Optional `buyerProfile:{structure:"individual"|"company"|"cooperative",name?}`. | Existing own-account registration envelope; exact legacy payload is in `authController.register`. | `422 VALIDATION_FAILED`, `INPUT_BUYER_PROFILE_INVALID`; profile starts private and unverified. Do not treat buyerProfile as KYC. |
| `POST /api/auth/login` | `{email,password,role?}`; role is only a legacy hint, not authority. | Existing token/session login envelope from `authController.login`; MFA may require second factor. | `401 AUTH_INVALID_CREDENTIALS`; `409 AUTH_IDENTITY_REVIEW_REQUIRED`; `422 AUTH_CREDENTIALS_INVALID` / `AUTH_ROLE_HINT_INVALID`. |
| `POST /api/auth/login/second-factor` | Exact JSON body `{challengeId,code}`; both are strings and `challengeId` identifies the live login challenge. | `200 {user:<authenticated account DTO>,token:<Bearer JWT>}`. | Login challenge expires after five minutes and is consumed on success. It is bound to the account auth version; factor validation allows five attempts before the factor lock. Errors include `AUTH_CHALLENGE_INVALID`, `AUTH_FACTOR_REQUIRED`, `AUTH_FACTOR_CODE_INVALID`, `AUTH_FACTOR_RATE_LIMITED`, `AUTH_IDENTITY_REVIEW_REQUIRED`. |
| `GET /api/auth/account` | Bearer. | Authenticated account DTO from route handler, including current account/session context. | Identity-only route; not a replacement for profile permissions. |
| `GET /api/auth/sessions` | Bearer. | `200 {sessions:[{id,createdAt,expiresAt,current}]}` for active unexpired sessions. |
| `DELETE /api/auth/sessions/others`, `DELETE /api/auth/sessions/:id`, `POST /api/auth/logout` | Bearer; no request body. | Revoke returns `{revoked:<count>}`; a missing per-session ID returns `404 AUTH_SESSION_NOT_FOUND`. Logout returns `{message:"Signed out."}`. Server revocation disconnects matching sockets. |
| `POST /api/auth/forgot-password`, `/resend-verification` | Exact body `{email,role?}`; `role` is a legacy hint only. | Rate-limited generic `202 {code:"AUTH_EMAIL_REQUEST_ACCEPTED",message}`; never reveals account existence. |
| `POST /api/auth/reset-password` | `{token,password}`; one-use 43-character proof and current password rules. | `{message:"Password reset successfully. Sign in again."}`; sessions are revoked. |
| `GET /api/auth/verify-email/:token`, `POST /api/auth/verify-email` | GET uses the path token; POST body is `{token}`. | `{message:"Email verified successfully. You can now log in."}`; both consume the same bound proof. |
| `POST /api/auth/phone-verification` | Empty JSON object plus `Idempotency-Key` (8–100 safe characters); destination is the persisted account phone. | `202 {id,state,expiresAt,sentAt,verifiedAt,errorCode}`. Provider policy/keys and Termii configuration gate delivery. |
| `GET /api/auth/phone-verification/history?limit=25&before=<id>`, `GET /:id`, `POST /:id/verify`, `DELETE /:id` | Verify body exactly `{code:string}`; status/cancel have no body. | Challenge DTO `{id,state,expiresAt,sentAt,verifiedAt,errorCode}`; history `{events:[{id,challengeId,action,attempt,at,errorCode?}],nextCursor}`. Challenge binds current session, auth version, phone and expiry. Phone proof is not KYC. |
| `GET /api/auth/two-step`, `POST /two-step/enroll`, `POST /two-step/confirm`, `POST /step-up`, `POST /step-up/:id/verify` | Factor/challenge bodies are controller-defined; authenticated for enrollment/step-up. | Challenge/enrollment status DTOs. | Rate limited; do not log codes or secrets. |

For sensitive routes, obtain a current server challenge, then send its token as `X-Step-Up-Challenge` on the exact mutation. The challenge is bound to HTTP method, path, selected profile, request body and, for file uploads, the submitted file digest. A changed body/file requires a new challenge. Profile evidence upload now parses the bounded multipart request before step-up consumes the challenge, so the upload digest is checked against the actual file bytes. See [Pass 01–03 remediation](20-pass01-03-contract-remediation.md#1-bound-step-up-and-profile-evidence-uploads) for the exact digest field and request sequence. Failures include `AUTH_STEP_UP_REQUIRED`.

## Verification and eligibility

- `GET /api/profiles/current/onboarding/evidence/contract` returns the active evidence contract. Use it before showing evidence purposes/types.
- `GET/POST /api/profiles/current/onboarding/evidence`; upload multipart part `file` (one configured supported file; route limits apply), with evidence metadata in allowed form fields. Upload, retry and removal require the current holder profile; upload/retry/remove are step-up protected. List/read/content routes are profile-private and never return the storage URL.
- `POST /api/profiles/current/verification-cases` submits a versioned snapshot; `GET` list/detail/history; `POST /:id/state` is applicant transition only. The current applicant submits; independent staff reviews through `/api/admin/verification-cases` or `/company-verification-cases`.
- For verification-case submission, `people` is an array with one `{path,route,country}` per declared person in the current draft. Paths derive from draft fields: `directors[0]`, `beneficialOwners[0]`, `executiveMembers[0]`, `authorizedSignatories[0]`, and/or `principalAgent`. `route` is `nigerian|international`; `country` is a two-letter ISO country code and Nigerian route requires `NG`. The draft contains the identity/evidence references; the case `people` array supplies route/country only. Extra, missing or duplicate paths fail `INPUT_VERIFICATION_PEOPLE_INVALID`. Case body is `{expectedDraftVersion,operationKey,people}` plus applicable individual `{identityRoute,identityCountry,identityEvidence}` fields. |
- `GET /api/auth/account`, profile switcher and verification DTOs are separate. Registration role hints and account-level flags do not grant company permission, KYC approval, publication, payout or step-up.
- Legacy `POST /api/verification/submit` and `PATCH /api/verification/review/:userId` remain mounted for compatibility but return `409 CONFLICT_KYC_PROFILE_WORKFLOW_REQUIRED`; do not wire them.

## Seats and organization billing

Current endpoints include `GET /current/seat-plans`, `/current/seats`, `/current/seat-purchases`, `POST /current/seat-purchases`, `GET /current/seat-purchases/:purchaseId[/audit]`, `POST /:purchaseId/cancel|reconcile`, and `POST /current/seats/:membershipId/renew`. Purchase body `{membershipId,planKey,operationKey}` returns `201 {purchase:{...safePurchase,redirectUrl?}}`; same key/profile/payload is idempotent. Seat plan response may be `{state:"configured",revision,currency:"NGN",plans:[...]}` or `{state:"unconfigured",plans:[],errorCode:"FEATURE_POLICY_UNCONFIGURED"}`. Payment callbacks, not client redirects, activate entitlements. The profile admin must hold current `team.manage`, correct organization permission and step-up on purchase/cancel/reconcile/renew. Revoked/expired/unpaid seats deny subsequent requests.

Publication plan purchase routes mirror the seat purchase lifecycle under `/current/publication-plans`, `/current/publication-plan`, `/current/publication-plan-purchases`. Payout setup routes `/current/payout-setup` and `/history`, POST start/reconcile/revoke require current profile permission and step-up. Provider readiness does not equal payout approval.

`GET /api/profiles/current/seats` returns `{profileId,includedHolderSeat,paidSeats:[{membershipId,identityId,role,state,acceptedAt,membershipExpiresAt,entitlement:{source,startsAt,expiresAt,active}|null,pendingPurchase:{plan,state,reference,createdAt}|null,version}],counts:{paidActive,paidPending,totalMembers}}`. Seat purchase records expose `{id,profileId,membershipId,plan,reference,state,entitlementId,paidAt,fulfilledAt,refundedMinor,createdAt,redirectUrl?}`; receipt is included only after payment and contains `purchaseId,reference,profileId,membershipId,planKey,planLabel,amountMinor,currency,durationDays,paidAt`. Plans are read from approved `profile_seats` Console policy; unconfigured policy returns `{state:"unconfigured",plans:[],errorCode:"FEATURE_POLICY_UNCONFIGURED"}`. Purchase request is `{membershipId,planKey,operationKey}`; renewal is `POST /current/seats/:membershipId/renew` with `{planKey,operationKey}`. These mutations require the holder-administrator and current signatory, step-up, verified contact, approved seat policy and current organization authority. Same operation key/payload replays; different payload conflicts. Paystack outcome ambiguity remains pending/reconciliation-required and does not activate a seat.

Payout setup `GET /api/profiles/current/payout-setup` returns `{profileId,policy:{state:"configured",revision,provider,currency,defaultSplitPercentage,approvedUntil}|{state:"unconfigured",errorCode},providerActivation:{available,errorCode?},setup:PayoutSetupDTO|null,ready:boolean}`. `PayoutSetupDTO` is an allowlist: `{id,profileId,version,state,current,provider,currency,bankCode,bankName,maskedAccountNumber,verifiedAccountName?,accountNameMatched,splitSettlementReady,splitPercentage,policyRevision,approvedUntil,failureCode,createdAt,updatedAt}`; the full account number is never returned. Start is `POST /current/payout-setup` body `{expectedVersion,operationKey,bankCode,accountNumber}` and returns a safe setup DTO (202 while provider work is pending, otherwise 200). Reconcile is `POST /current/payout-setup/:setupId/reconcile` with an empty object; revoke is `POST /current/payout-setup/revoke` with `{expectedVersion,reasonCode}`. Reads/history and mutations are limited to the eligible holder-administrator with `payout.manage`; organization profiles additionally require current approved signatory authority, minimum current KYC, step-up, and an approved `profile_payout_setup` Console policy. `bankCode` must come from the configured provider directory. Monnify credentials/provider availability and approved split policy are activation dependencies; an unavailable or expired policy returns a safe 503 and does not imply payout readiness.

## Frontend state guidance

Keep account and selected-profile stores separate. After login, load `/api/profiles`, select only a returned profile, then send its ID on each profile-scoped request. On `401`, clear session state; on `403` profile/seat/mandate/department errors, refresh current profile/permissions and do not retry under another profile automatically. On profile switch, cancel stale queries, clear private caches and restart socket subscriptions. Use exact `expectedVersion` values for mutations. Never display organization-only fields to a member merely because the account holder belongs to that organization.

### Organization roster and authority DTOs (source-checked)

The following shapes are the current service projections, not a generic role system:

- `GET /api/profiles/current/members?after=<membershipId>&limit=50` returns `{members:[MemberDTO],nextCursor}`. `MemberDTO` is `{id,profileId,identityId,role,customRoleId?,deniedPermissions,state,ownerSeat,assignedOnly,assignedResources:[{kind,id}],negotiationLimit?:{amount,currency},expiresAt?,version}`. The service permits at most 100 rows per page. `GET` requires current `team.manage`.
- `POST /api/profiles/current/members` directly adds a known identity using `{identityId,role,customRoleId?,deniedPermissions?,assignedOnly?,assignedResources?,negotiationLimit?,expiresAt?}` and returns `201 {member:MemberDTO}`. `PATCH /current/members/:id` takes `{expectedVersion,role?,customRoleId?,deniedPermissions?,assignedOnly?,assignedResources?,negotiationLimit?,expiresAt?}`; removal is `POST /current/members/:id/remove` with `{expectedVersion}`. Both return `{member}`. Writes require step-up, current `team.manage`, and cannot alter/remove the included owner seat. Assignments are typed `property|project|enquiry|conversation`; grants cannot exceed the caller's current effective permissions.
- Invitation issue is distinct from direct member addition: `POST /api/profiles/current/invitations` body `{email,grant,operationKey}` where `grant` is the same role/assignment subset accepted above; success is `201 {invitation:{id,profileId,state,version,expiresAt,acceptedAt?,membershipId?,delivery:{state,attempts,code}}}`. The opaque invite token is delivered out of band and is never returned. Claim is `POST /api/profiles/invitations/claim` with `{token}`; the claim operation creates/activates the membership when issuer and entitlement checks still pass. The compatibility accept route is `POST /api/profiles/invitations/:id/accept`, where `:id` is the membership ID, with `{expectedVersion}`; it accepts only the matching invitee's current invited membership. Both paths require the invitee's verified identity and current issuer authorization; `pending_entitlement` does not grant active profile access.
- Role permissions are server-owned keys: `dashboard.read`, `team.manage`, `roles.manage`, `listing.read`, `listing.edit`, `listing.price`, `listing.media`, `listing.publish`, `listing.boost`, `listing.confirm`, `project.edit`, `enquiry.read`, `enquiry.reply`, `message.read`, `message.reply`, `negotiation.read`, `negotiation.propose`, `terms.accept`, `viewing.manage`, `document.read`, `document.share`, `document.request.approve`, `document.issue`, `payment.read`, `payment.initiate`, `payment.manage`, `escrow.read`, `escrow.claim`, `payout.manage`, `notification.read`, `notification.preferences`, `personalisation.read`, `personalisation.manage`. Built-in roles are `administrator`, `sales_agent`, `project_editor`, `finance`, `viewer`, plus profile-scoped `custom`; `staff` is not grantable through organization role APIs. `POST /current/roles` body `{name,permissions}`; `PATCH /current/roles/:id` body `{name,permissions,expectedVersion}`; `POST /current/roles/:id/state` body `{enabled,expectedVersion}`.
- A mandate request is `POST /api/profiles/current/mandates` with `{agentProfileId,resourceKind,resourceId,type,permissions,startsAt,expiresAt}`; `type` is `sole|exclusive|open`. Resource-specific permission keys must be from the server mandate allowlist, and `open` cannot grant edit/boost capabilities. State actions use `POST /current/mandates/:id/:action`: `accept` requires `{expectedVersion,conflictDeclared:boolean}`; `terminate`, `take-editor`, and `return-editor` require `{expectedVersion}`. Responses are `{mandate:MandateDTO}` where the DTO contains `id,ownerProfileId,agentProfileId,resourceKind,resourceId,type,permissions,state,startsAt,expiresAt,version`. Current owner/signatory and verified agent checks remain authoritative.
- Signatory submission is `POST /api/profiles/current/signatories` with exactly one of `authorityEvidenceId` or `authorityDocumentId`, plus `{identityId,expiresAt}`. Staff review is `POST /api/admin/profile-signatories/:id/review` with `{decision:"approved"|"rejected"|"revoked",expectedVersion}`. Responses expose only `{id,profileId,identityId,state,expiresAt,reviewedAt,version}` plus safe revocation fields; authority files remain private. Approval requires current membership, approved organization verification roster, current individual KYC, matching current clean authority evidence and an independent Legal & Verification reviewer.
