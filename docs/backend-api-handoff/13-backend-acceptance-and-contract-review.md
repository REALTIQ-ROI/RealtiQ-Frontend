## Final two internal implementation changes

### Recommended ranking

**Source conclusion: implementation present; policy/data activation remains gated.** `src/services/profileCompletenessRankingService.js` reads the approved versioned `profile_completeness_criteria` Console policy and scores only fields in `PUBLIC_PROFILE_COMPLETENESS_FIELDS`, after applying `serializePublicProfileCard`. It does not read client-supplied scores or private KYC/onboarding data. `src/constants/consolePolicies.js` validates allowed field names, uniqueness, source reference and weights summing to one. `src/services/sponsoredPlacementService.js` reads approved `sponsored_placements`, filters to active/current time windows, and then checks current eligible published property/project, active unrestricted profile, current holder account and advertiser verification provenance. Client Booleans and payment records are not ranking authority. `canonicalCatalogueService.js` applies approved `recommended_weights`, detects unavailable positive-weight inputs, discards partial scores and returns deterministic newest fallback notices. Highest Rated and Trust Tier use deterministic Recommended ties when available and stable recency/ID ties otherwise.

Mounted public consumers `/api/properties`, `/api/properties/map`, `/api/projects` canonical grouping, `/api/projects/map`, project matching units and shared facets use the canonical search path. Ranking signal integration is shared at the query boundary; UI should not compute scores. The ranking policy needs two-person approval and the relevant criteria/placement revisions must be approved. No runtime ranking execution was verified here.

### Data-rights execution

**Source conclusion: required per-record actions and fences are present; destructive operation remains approval/configuration gated.** `src/services/dataProtectionDeletionService.js` classifies individual-profile identity records for anonymization, private self-verification evidence for deletion, terminal requester-only verification cases for redaction, and eligible non-evidentiary support documents for removal. It distinguishes current/pending/shared/organization/title/ownership/financial/legal evidence as preserved or review-blocked. Retention triggers are record-specific. `recheckDeletionItem` rechecks request/profile/holder scope, current staff reviewer authority, retention revision and legal holds immediately before execution. Per-item state, reason and audit outcomes are persisted. `src/services/dataProtectionExecutionService.js` batches/resumes jobs, leases workers and exposes partial outcomes. The legacy support-document path permits a missing owner-profile binding only when the document belongs to the requester and the primary individual profile binding is established; otherwise it is preserved/review-blocked.

Destructive execution still requires explicit execution enablement plus the approved current retention policy; a missing key/storage integration leaves private bytes inaccessible and cleanup safely pending/failing. This review did not execute a deletion job.
