# First-batch frontend integration tracker

Updated: 2026-10-25. Scope: this frontend repository only; the backend is unavailable here. Status describes the named operation, not an entire route family. COMPLETE means its frontend call and relevant UI states are wired locally, not live-backend accepted. PARTIAL means supported work remains. BLOCKED BY CONTRACT names a missing or contradictory contract; BLOCKED BY CONFIGURATION names an activation gate. NOT STARTED means frontend work remains, and NOT APPLICABLE means the handoff excludes the operation.

## Contract rules applied

- Endpoint-specific response shapes are retained; no universal `{success,data}` envelope is assumed.
- 401 clears session state; 409 viewing version conflict reloads; validation responses retain field errors; configuration/provider errors retain their API code and request ID.
- Private state is reloaded after a profile change. A server 403 remains authoritative even if a client affordance was visible.
- Tour cancellation is absent by design because no mounted first-batch cancel action exists.

## Current contract boundaries

- The 156-field dictionary is present, but the response DTO for `GET /api/properties/field-dictionary` and property-level effective provenance/readiness projection are not specified. The owner form exposes only fields with safe, known serialization. Full canonical form and persisted incomplete-draft workflow remain frontend work plus these endpoint details.
- Profile-evidence multipart upload is blocked by the documented middleware order: step-up runs before file parsing, so its challenge cannot bind uploaded bytes. Holder evidence/case reads and withdrawal, plus staff queue/detail/history/claim/rejection/evidence reads, are integrated. Case creation remains blocked by the undocumented current-onboarding response DTO needed for the current draft version and declared people paths; approval remains blocked by the missing approved manual-source policy DTO and check-specific validation schema.
- Failed project publication responses discard field-level blocker details in the backend serializer. Successful publication returns blocker rows; failures can show code/message and refresh available readiness.
- Applicant privacy execution returns outcome groups, not individual record IDs, hold IDs or per-record dates. A true per-record table needs an expanded API response.
- Paid/live viewing purchase remains withheld because the mounted fixed-price route conflicts with the launch flow. No tour cancellation endpoint is supported.
- Other unconnected mutations are marked per operation above. The existence of a step-up challenge no longer makes every sensitive JSON mutation a contract blocker.
