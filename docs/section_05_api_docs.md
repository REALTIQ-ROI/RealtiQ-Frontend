# Group 05 API documentation — Property and project supply

**Contract baseline:** current mounted backend source in this repository. This document covers seller-side individual properties and developer projects, unit types and units, plus the import/grid routes that create or mutate that inventory. It is not a claim that provider services are live.

## 1. Governing scope and source traceability

Read together: REALTIQ PRD §§7 (listing lifecycle and listing facts), 8 (developer project/type/unit inventory), and 13 (seller lifecycle, review, archive and relisting); Specifications RQS-04 A–M, RQS-02 §§2–10, RQS-06 §§5 and 8–10, RQS-01 §§5, 18 and 19, and RQS-05 §13. Specifications govern a conflict. The runtime canonical source is `src/constants/sourceListingFields.js` (156 definitions); the field dictionary/validator/inheritance and API consumers are identified below.

Scope rules reflected by the API:

- Individual listings and project inventory use the same canonical dictionary but only fields applicable to the target entity can be written there. Project flow is Project → Unit Type → Unit. Effective values resolve from the closest explicit value, with provenance returned to authorized management projections.
- Property and project drafts can preserve incomplete answers. A draft can be saved with `publicationAction: "save_draft"`; a listing can be submitted for review by omitting it or by the supported submission action. Draft omission, explicit `null`, `false`, numeric zero, POA and `unset` are distinct states.
- Project units must reference a current unit type. `unitTypeQuantity` is the declared inventory limit; new unit creation/import/type moves are rejected when the type has no remaining declared capacity. Unit IDs are unique within a project. Public reference IDs are system-generated and read-only.
- `Sold` is transaction-generated and is not an ordinary seller/grid availability edit. Unit/public listing states and publication review are separate. Sale price, reserve, title evidence and other private/system-owned facts are not made public by this contract.
- A selected-unit project publication updates only the selected ready units; other already-published units that remain ready stay published. Previously published units that are no longer ready are unpublished.
- `DELETE /api/properties/:id` is retained as a compatibility route but archives the property and retains transaction/history records. `DELETE /api/projects/:id` is not an archive operation: it removes only a project with no linked units and conflicts otherwise. No general project archive contract is inferred.
- Typed unit identifiers are supported by the unit APIs and spreadsheet import. The source permits a typed list as an alternative to generated identifiers. The backend does not expose a separate server-side unit-number pattern preview/generation endpoint; do not invent a pattern grammar or present local generation as server-side confirmation.
- No-merge duplicate behavior, ownership evidence, review and relisting are enforced by their dedicated workflows. Do not infer a duplicate by a client-side match or fabricate a size tolerance.

## 2. Shared request and response semantics

- API base: `/api`; routers are mounted in `src/app.js` at `/api/properties` and `/api/projects`.
- Authenticated mutations use the bearer session and current selected profile (`X-Profile-ID` where multiple profiles are active). Resource authorization is rechecked against the current profile, membership/seat and resource ownership at execution time. Admin access uses current staff profile/department authority; frontend role checks do not grant access.
- Seller writes require the corresponding resource permissions: `listing.edit`, `listing.publish`, `listing.price`, `listing.media`, `project.edit`, and current owner/signatory authority where the workflow requires it. Project creation is developer-profile-only and checks current identity/developer verification and company eligibility. Internal Audit is read-only. Listing Quality review is separated from the submitting seller.
- Step-up is enforced by route middleware for protected mutations. Some middleware is conditional based on the submitted action/fields; the backend step-up protocol and `X-Step-Up-Challenge` contract remain authoritative. Send the challenge header when the request is challenged; bind the challenge to the exact method, path, active profile, JSON body and/or file digest as required by that route.
- Resource versions are integer `version`/`expectedVersion` values; type mutations additionally use `expectedTypeVersion`. Send the latest versions returned by the corresponding management DTO. A `409` means reload and reconcile; do not automatically replay a mutation with a stale version.
- Shared errors use the application error envelope; stable codes cited below are the route/service codes. Validation errors may carry allowlisted `details.listingErrors`, `details.projectBlockers` or unit blockers. Never display raw internal error objects.
- Public property/project endpoints use eligible public projections. Owner/staff management endpoints have `private, no-store` behavior where registered. Never expose private reserve, actual sale price, title evidence bytes, provider URLs or private identity data in public views.

### Canonical field mutations

`canonicalFields` is used on create; `canonicalFieldMutations` is used on updates. Supported operations are:

```json
[
  { "field": "bedrooms", "operation": "set", "value": 3 },
  { "field": "powderRooms", "operation": "set", "value": 0 },
  { "field": "commercialRoomCount", "operation": "set_null" },
  { "field": "optionalField", "operation": "unset" },
  { "field": "unitField", "operation": "reset_to_inherit" }
]
```

The names above illustrate mutation semantics; a field may use only operations permitted by its dictionary metadata and entity level. `set` requires the `value` property (including explicit `false` and `0`); `set_null` records explicit null only for fields declared nullable; `unset` removes an unanswered value; `reset_to_inherit` removes a unit override so the next parent value becomes effective. Do not convert empty/false/zero/null/unset/POA into each other.

## 4. Individual property lifecycle APIs

### `GET /api/properties/mine`

Bearer auth, registered active seller profile; returns the current profile's own listings (private/no-store). Query accepts `page` (default 1, range 1–10000) and `limit` (default 20, range 1–100) only. Success: `{ "properties": [<owner-safe property DTO>], "pagination": { "page": 1, "limit": 20, "total": 0, "pages": 0 } }`.

### `POST /api/properties`

Bearer auth; `verified` access-level middleware; active owner/developer/agency profile with `listing.edit`. Non-draft submission also needs `listing.publish`, current minimum KYC, signatory authority and no outstanding seller fee recovery. `listing.price` and `listing.media` are additionally required when those values/references are supplied. Step-up middleware is conditional for protected creation/commercial input.

Request JSON accepts supported legacy compatibility fields and canonical input. The canonical form is preferred:

```json
{
  "publicationAction": "save_draft",
  "canonicalFields": {
    "headline": "Example source-defined listing title",
    "propertyType": "<dictionary value>",
    "category": "<dictionary value>",
    "streetAddress": "<permitted public address>",
    "askingPrice": 50000000,
    "currency": "NGN",
    "bedrooms": 3
  },
  "media": []
}
```

The property field values above are examples only; use actual dictionary allowed values. `publicationAction` on create may be `save_draft`; omit it to submit a standalone listing for review. Project-unit creation additionally requires `projectId` and `canonicalUnitTypeId`; its canonical fields may contain only unit-owned values or values equal to inherited parent values. Parent facts must be edited on their parent record. Unit quantity/capacity and unique unit identity are checked before persistence. Media references must resolve through current profile-authorized asset workflows.

Success: `201` with `{ "property": <authorized property DTO>, "titleDocuments": [], "titleVerifications": [], "riskDetected": false, "message": "..." }` (fields are included according to the create flow). A project unit is not public merely because it was created; it must pass project/type/unit readiness and be approved/published through the project workflow.

Important errors include `LISTING_REQUIRED_FIELDS_MISSING`, `LISTING_CANONICAL_FIELDS_REQUIRED`, `LISTING_FIELDS_INVALID`, `LISTING_FIELD_LEVEL_INVALID`, `CONTENT_UNIT_TYPE_REQUIRED`, `CONTENT_UNIT_TYPE_NOT_FOUND`, `CONTENT_UNIT_TYPE_QUANTITY_REQUIRED`, `CONFLICT_UNIT_TYPE_QUANTITY`, `CONFLICT_UNIT_IDENTIFIER`, `LISTING_CANONICAL_ALIAS_CONFLICT`, `AUTH_KYC_REQUIRED`, and permissions/resource conflicts.

### `PATCH /api/properties/:id`

Bearer auth; current resource owner/profile or properly authorized staff; the seller must have listing permissions. Step-up is conditional for submission or protected commercial changes.

Request accepts the property update contract from `profileListingService.update`: allowlisted legacy editable values and/or `canonicalFieldMutations`, plus optional `expectedVersion` and publication action. Use the current `expectedVersion` from the private DTO even where compatibility makes it optional. To save draft, send `publicationAction: "save_draft"`. To submit for review, use the source-supported submission action (`submit_for_review`) when present in the route contract; never send arbitrary `publish: true` to directly make a listing public. The service validates readiness and moves it into review; only staff review can approve it.

Success: property DTO with canonical/effective fields, provenance and version as authorized. Stale version returns `409 CONFLICT_LISTING_VERSION`; invalid canonical fields return `422 LISTING_FIELDS_INVALID` with allowlisted `details.listingErrors` when available. Sold/transaction-protected records cannot be edited as ordinary active supply.

### `DELETE /api/properties/:id` (archive compatibility route)

Bearer auth, current owner/resource authorization, step-up. Optional body is version-aware per `profileListingLifecycleService.archive`; use the latest `expectedVersion` if available. Returns `{ property, version, state: "archived", replayed }`. This does not physically delete the record or transaction history.

### `PATCH /api/properties/:id/approval`

Bearer auth, admin staff context, step-up, current Listing Quality authority and independent review. Body: `{ "decision": "approve" | "reject", "rejectionReason": "..." }` (reason required on rejection per handler validation). The handler uses the current property version it loaded; clients should first load `GET /api/properties/:id/admin-review`. Success: `{ "property": <staff review projection>, "message": "..." }`. Approval still requires readiness, current seller eligibility, non-duplicate/ownership/title conditions and approved unit-type linkage for project units. The service, not client state, decides visibility.

### Property detail/read paths

- `GET /api/properties/:id` — public eligible projection; optional auth does not elevate private visibility.
- `GET /api/properties/:id/owner-detail` — authenticated profile-scoped private detail.
- `GET /api/properties/admin/pending-approval` and `GET /api/properties/:id/admin-review` — admin staff review projections, with current staff authority.
- `POST /api/properties/:id/confirm-details` — authenticated freshness confirmation.
- `GET /api/properties/:id/price-history` and `/price-history/chart` — public-safe asking-price history only; reserve/actual sale price remain private.
- `GET/POST /api/properties/:id/listing-verification...` — separate listing-verification evidence workflow; it does not replace seller identity/title requirements.
- Title document metadata/content uses the protected workflow: `GET /api/properties/:propertyId/title-documents`, `GET /api/properties/:propertyId/title-documents/manage`, and `POST /api/properties/:propertyId/title-documents` (multipart `file`, property-scoped authorization and step-up). Canonical title declarations are not file uploads; use protected document APIs for evidence.
- Duplicate/relist review is an explicit, no-auto-merge workflow:
  - `GET /api/properties/:id/duplicate-candidates` (auth, private/no-store) returns `{ sourceVersion, candidates: [{ propertyId, publicReference, title, status, updatedAt, matchedSignals, relistAllowedByBuyerOfRecord, transferEvidenceRequired }], nextAction }`. Candidate IDs are exact property IDs; matching signals do not grant a merge.
  - `POST /api/properties/:id/duplicate-links` requires verified access, step-up and current `listing.edit`. Body: `{ operationKey, expectedUpdatedAt, candidatePublicReference, samePhysicalProperty: true, reason?, transferProofDocumentId? }`. `operationKey` is 8–100 `[A-Za-z0-9_-]`; `candidatePublicReference` is 4–80 `[A-Za-z0-9_-]`; reason is optional, on-platform text ≤500. A sold candidate not owned by the recorded buyer requires privately attached, validated transfer proof. Response `201 { link: { id, propertyId, canonicalPropertyId, state, sameOwnerProfile, version, createdAt, decidedAt } }`. A same-owner, unsold pair can be approved directly; other pairs enter `authority_review`.
  - `GET /api/properties/:id/duplicate-links?before=<link-id>&limit=25` returns `{ links: [<link DTO>], nextCursor }`; `limit` 1–100. `POST /api/properties/:id/duplicate-links/:linkId/withdraw` requires step-up and body `{ expectedVersion }`; only the proposing profile can withdraw an active request.
  - Staff review is `GET /api/admin/duplicate-property-matches?before=&limit=` (Listings Quality or Legal Verification, Internal Audit excluded), evidence list/content under `/api/admin/duplicate-property-matches/:id/evidence...`, and `POST /api/admin/duplicate-property-matches/:id/decision` (step-up). Decision body requires `decision: approve|reject`, nonempty on-platform `reason` ≤500 and `expectedVersion`; approval also requires both current private authority document IDs for unsold cross-owner matches, or the exact submitted `transferProofDocumentId` for a sold candidate. Returned link states include `approved`, `authority_review`, `rejected`, `withdrawn` and `stale`.
  - Buyer-of-record sold relisting is authorized only when the current owner matches the recorded buyer and the exact source-defined property match is revalidated. Other sold relists require transfer evidence and independent review. Never use creator identity or client claims as proof.
- Availability may be edited only through the supported listing/grid transition contract and does not grant permission to mark a record sold. Project-unit bulk availability uses the durable job route with `action: "availability"` and `targetAvailability`.

## 5. Project, unit-type and unit lifecycle APIs

### `POST /api/projects`

Bearer auth, verified access level, selected `developer` profile, `project.edit`; checks identity KYC, developer profile verification, company eligibility, and conditional `listing.price`/`listing.media`. Project creation accepts `publicationAction: "save_draft"`; create does not directly publish inventory.

```json
{
  "publicationAction": "save_draft",
  "canonicalFields": {
    "projectName": "Example Development",
    "developmentStructure": "<dictionary value>",
    "projectDescription": "On-platform description"
  },
  "media": []
}
```

`canonicalFields` must only contain project-applicable dictionary keys. Legacy `name`, `projectType`, description, amenities, media and location fields remain accepted where the current allowlist permits them; conflicting legacy/canonical aliases return `409 LISTING_CANONICAL_ALIAS_CONFLICT`. Success `201`: `{ "project": <project management DTO> }`.

### `GET /api/projects/mine` and `GET /api/projects/:id/manage`

Bearer auth/current profile; own project list and private management detail. `GET /api/projects/mine` query accepts `page` (1–10000, default 1), `limit` (1–100, default 20), `sort` (`newest`, `price_asc`, `price_desc`), `search`, `publicationState` (`published`, `unpublished`), and scalar filters `projectType`, `state`, `city`, `area`. Response: `{ "projects": [<project card DTO plus ownerProfileId and version>], "total": <integer>, "page": <integer>, "limit": <integer> }`. Detail returns `{ "project": <DTO> }`. Project DTO includes version; owner receives authorized canonical values, unit types, effective fields/provenance and publication diagnostics; staff/public DTOs are allowlisted.

### `PATCH /api/projects/:id`

Bearer auth/current project profile; `project.edit`; conditional permissions for commercial/media values and step-up for protected publication/commercial mutations. `expectedVersion` is supported; send it for every update. Create uses `canonicalFields`; update uses `canonicalFieldMutations` (1–200 mutations). Supported `publicationAction` values on update: `save_draft`, `publish_all_ready`, `publish_selected`. `selectedUnitIds` is permitted only with `publish_selected`, must be unique valid IDs and is bounded by the configured grid request limit.

```json
{
  "expectedVersion": 4,
  "publicationAction": "publish_selected",
  "selectedUnitIds": ["<approved-ready-unit-id>"],
  "canonicalFieldMutations": [
    { "field": "projectDescription", "operation": "set", "value": "Updated on-platform description" }
  ]
}
```

Publication request may omit `canonicalFieldMutations` when only publishing. It requires current owner signatory, developer/company eligibility, no blocked seller fee recovery, approved project/type/unit readiness and current versions. `publish_selected` rejects units not approved, belonging to another project, or blocked. The controller wraps the service result, so success is `{ "project": { ...<project DTO>, "version": <integer>, "publication": { "published": <boolean>, "publishedUnitCount": <integer>, "blockedUnitCount": <integer>, "blockedUnits": [{ "unitId": "...", "blockers": [{ "field": "...", "code": "..." }] }], "projectBlockers": [] } } }` (optional blocker arrays may be omitted). The selection is additive to the existing ready published inventory; unselected still-ready published units remain published.

### `GET/POST/PATCH/DELETE /api/projects/:projectId/unit-types[/:unitTypeId]`

Authenticated current project scope, `project.edit`; create/update/delete require step-up middleware and verified developer/resource authority. Read also returns `unitTypeImpact` at `GET .../:unitTypeId/impact`.

Create:

```json
{ "expectedVersion": 4, "canonicalFields": { "propertyType": "<dictionary value>", "unitTypeQuantity": 12, "askingPrice": 50000000, "currency": "NGN" } }
```

The exact canonical fields depend on the dictionary. Success `201`: `{ "unitType": { "id": "...", "version": 0, "projectVersion": 5, "canonicalFields": {}, "effectiveFields": {}, "fieldSources": {}, "media": [] }, "projectVersion": 5 }`. Owner-only reserve information is never included in public/staff projections.

Update body: `{ "expectedVersion": <projectVersion>, "expectedTypeVersion": <typeVersion>, "canonicalFieldMutations": [<1–200 canonical mutations>] }`. Response `{ "unitType": <unit type DTO>, "impact": <impact DTO>, "projectVersion": <integer> }`. Parent changes recalculate effective values. Affected units are marked `needs_review`/unpublished and search projections invalidated; they must be republished after readiness.

Delete body: `{ "expectedVersion": <projectVersion>, "expectedTypeVersion": <typeVersion> }`. Response `{ "removed": true, "projectVersion": <integer> }`. Deletion is rejected with `409 CONFLICT_UNIT_TYPE_HAS_UNITS` when any current or historical unit references the type. This is not an archive path.

Version mismatch: `409 CONFLICT_UNIT_TYPE_VERSION` or `CONFLICT_PROJECT_VERSION`; malformed type IDs/body: `422 CONTENT_UNIT_TYPE_INVALID` / `CONTENT_VERSION_INVALID` / `CONTENT_UNIT_TYPE_FIELDS_INVALID`; missing resource: `404 CONTENT_UNIT_TYPE_NOT_FOUND`.

Project public-media addition is `POST /api/projects/:id/media`, authenticated in the active project profile with `listing.media`, body `{ "media": [<authorized public media references>], "expectedVersion": <optional current project version> }` (the controller also accepts a single media item in the body). It returns `201 { "project": <authorized project DTO> }`. Private files are not accepted as public media; use protected document workflows. Parent/project media changes can invalidate child publication and projection state.

### Unit creation and project unit reads

- Create a project unit with `POST /api/properties`, supplying `projectId`, `canonicalUnitTypeId`, unique unit identity in canonical fields/legacy `projectUnit`, and only unit overrides. The route requires a current type from that project, owner-profile match, parent-equal values when a parent-scoped fact is repeated, and remaining `unitTypeQuantity` capacity.
- Read units via `GET /api/projects/:idOrSlug/properties`. Query accepts `page`/`limit` (same bounds as project list), `sort` (`newest`, `price_asc`, `price_desc`), `search`, `publicationState` (`published`, `unpublished`), `status` (`available`, `under_offer`, `sold`) and built `propertyType`. Public results include eligible published units only. `includeUnpublished=true` requires authentication and current project scope; response is private. Response: `{ "project": <project summary>, "properties": [<unit summary with effective canonical values/provenance as authorized>], "total": <integer>, "page": <integer>, "limit": <integer> }`. Unit-level effective search values are shared with catalogue/map filters.
- Unit availability and publication are distinct. Ordinary seller availability operations accept Available, Under Offer or Not released. Sold requires transaction evidence and is not a normal grid option.
- Unit IDs must be unique within the project across canonical `canonicalFields.unitIdentifier` and legacy `projectUnit.unitNumber`. The canonical validator accepts 1–80 ASCII characters matching `[A-Za-z0-9][A-Za-z0-9/-]{0,79}`. The identity service NFKC-normalizes and trims for cross-representation comparison; the canonical validator itself rejects whitespace that makes the value fail its pattern. Pattern and typed-list selection are UI inputs; public property reference IDs remain system-generated. `409 CONFLICT_UNIT_IDENTIFIER` indicates a collision; inconsistent canonical/legacy IDs return `409 LISTING_CANONICAL_UNIT_ID_CONFLICT`.

## 6. Publication readiness and state transitions

Property review and developer publication are separate:

| Object | Current source states/action | Result |
|---|---|---|
| Property draft | `approvalStatus: draft` → submit/review | `pending_review`; not public |
| Property staff review | `decision: approve` / `reject` | `approved` or `rejected`; approved only if readiness/authority checks pass |
| Project | draft/edit → `publish_all_ready` or `publish_selected` | Project is public when project readiness passes and at least one eligible unit is public |
| Project unit | draft/blocked/unpublished → selected/all-ready publication | `published`, `blocked`, or `unpublished`; each unit must be approved and ready |
| Inventory availability | Available / Under Offer / Not released / Sold | Sold is transaction/system-owned; Not released is not publicly selectable |
| Property archive | `DELETE /api/properties/:id` | archived and retained |
| Project delete | `DELETE /api/projects/:id` | only with no unit records; conflicts otherwise; no general archive API |

Readiness errors use allowlisted field blockers, such as `LISTING_FIELDS_INVALID`, `CONTENT_PROJECT_PUBLICATION_NOT_READY`, `CONTENT_PROJECT_PUBLICATION_SELECTION_INVALID`, `CONTENT_CANONICAL_RECLASSIFICATION_REQUIRED`, `AUTH_DEVELOPER_VERIFICATION_REQUIRED`, and `CONTENT_UNIT_TYPE_REQUIRED`. Use the response `blockers`/`listingErrors` as authoritative and refetch after fixing parent data. Policies/providers may make location/site-plan/POA/commercial fields unavailable; these are safe gates, not permission to guess values.

## 7. Unit grid and durable operations

### Grid read/export

- `GET /api/projects/:projectId/unit-grid?page=1&limit=50&sort=newest` → `{ project, projectVersion, items, pagination: { page, limit, total, pages }, filters }`. Each item includes unit ID, versions, `rawOverrides`, `effectiveFields`, `fieldSources`, readiness and publication state.
- Supported query: `page`, `limit` (1–100), `sort` (`newest`, `price_asc`, `price_desc`, `availability`, `publication`, `unit_type`), `search`, `unitTypeId`, `availability` (`available`, `under_offer`, `sold`, `not_released`), `publicationState` (`published`, `unpublished`, `blocked`, `needs_review`, `archived`), `problemsOnly`, `minPrice`, `maxPrice`, `currency` (`NGN`/`USD`), `propertyType`. Price bounds require currency. Page range 1–10000.
- `GET .../unit-grid/export.csv` returns `text/csv`, private/no-store, filename `realtiq-project-units.csv`, and `X-Export-Row-Count`.

### Synchronous bulk edit

`POST /api/projects/:projectId/unit-grid/bulk`, step-up middleware; each row has a current unit version and exactly one of canonical mutations or a destination type ID. Top-level project version and an idempotency key are mandatory.

```json
{
  "operationKey": "grid-edit-2026-0001",
  "expectedProjectVersion": 7,
  "rows": [{
    "unitId": "<unit-id>",
    "expectedVersion": 2,
    "canonicalFieldMutations": [{ "field": "bedrooms", "operation": "set", "value": 3 }]
  }]
}
```

Rows are bounded by `firstBatchPolicies.grid.maxRowsPerRequest`; each row's mutation count is bounded by policy. Unsupported private/system/evidence/media fields are rejected. Result includes an operation summary, row outcomes, current project version and `replayed`; field edits can require re-review and invalidate the public projection.

### Durable grid jobs

`POST /api/projects/:projectId/unit-grid/jobs` returns `202 { "job": <job summary> }`. Job `action` values are source/API-defined: `field_edit`, `availability`, `price_adjustment`, `publish`, `unpublish`, `archive`, `confirm`. Payload includes `operationKey`, `expectedProjectVersion`, action-specific `actionOptions`, and versioned `rows`. Exact required actionOptions are validated per action; do not send options from another action. Job status is polled at `GET .../jobs/:jobId`; cancellation is `POST .../jobs/:jobId/cancel`. Worker rechecks active profile/resource authorization and lease/cancellation before mutating. Job states and row outcomes are returned by the job DTO; do not treat queued/processing as completion.

Common envelope: `{ "operationKey": "8–100 chars [A-Za-z0-9_-]", "expectedProjectVersion": 7, "action": "availability", "actionOptions": { "targetAvailability": "Under Offer" }, "rows": [{ "unitId": "<ObjectId>", "expectedVersion": 2 }] }`. `actionOptions` is exactly `{ "targetAvailability": "Available" | "Under Offer" | "Not released" }` for availability; exactly `{ "mode": "amount" | "percentage", "direction": "increase" | "decrease", "value": <positive number> }` for price adjustment (amount mode requires a positive safe integer); omitted for other actions. Rows are unique unit IDs with non-negative integer versions. Job size/request bytes are policy-bounded. Job states include queued, processing, completed, partially_completed, failed and cancelled; each row carries its state, attempts, optional error and operation/version/undo metadata. A job can finish partially; render per-row outcomes.

### Undo

`POST /api/projects/:projectId/unit-grid/operations/:operationId/undo` (step-up) returns the operation summary and current project version. The summary includes `undoAvailable` and, when configured, `undoExpiresAt`. Undo is allowed only for applied reversible operations within configured undo window, with current versions unchanged; conflicts must be resolved by refetching, not blind overwrite.

### Pause/withdraw controls

- Seller project withdrawal uses `PATCH /api/projects/:id` with the latest `expectedVersion` and either `publicationAction: "save_draft"` or the supported compatibility `unpublish: true` / `isPublished: false` form. This turns off the project and all its unit publications; it is not deletion.
- Admin status control is `PATCH /api/admin/projects/:id/status`, with bearer auth, selected staff profile, current Console project authority and step-up. Body accepts `{ "status": "draft" | "suspended", "expectedVersion": <integer optional> }`; status changes unpublish project units. This is not a seller archive API.
- Admin featured moderation is a separate `PATCH /api/admin/projects/:id/featured` and is outside seller publication state.
- Property Listing Quality review remains `PATCH /api/properties/:id/approval`; the seller cannot approve their own listing.

## 9. Configuration gates and known contract limits

The code has no fabricated geographic data, boundary, FX rate, POA price, duplicate size tolerance, site-plan media, payment terms or reserve. Those values remain controlled by `firstBatchPolicies.js`, versioned Console policies and provider datasets. Unconfigured policies return the existing safe unavailable/validation state. Public exposure also waits for publication eligibility and current verification.

Specific source-defined limit: the backend has quantity and unit identity validation, but no distinct endpoint that accepts a generation pattern and previews generated identifiers or atomically generates an entire unit type inventory. The UI may collect/preview explicit typed identifiers, but it must submit each unit through the supported create/import path, honor server conflicts/capacity, and not claim the generated pattern was confirmed by backend. A future pattern endpoint would require an authoritative exact generator grammar and transaction contract.
