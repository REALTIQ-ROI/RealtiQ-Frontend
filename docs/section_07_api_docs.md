# Group 07 API contract — trust, partners and public profiles

Source: PRD §§15, 17, 19; Specifications RQS-06 §§16–18 and RQS-07 §§4–7. This file describes mounted backend behavior. All prices are integer minor units. A Console policy record is not a provider activation.

## Shared request rules

Authenticated requests use `Authorization: Bearer <JWT>`. Profile-scoped calls require the current `X-Profile-ID` (an `AccountProfile` ID), and the backend rechecks the current session, active membership/seat, profile status and effective permission. Protected JSON mutations use `X-Step-Up-Challenge`, initiated against the exact method, URL, selected profile and JSON body via the existing bound step-up contract in `docs/frontend-handoff/19-frontend-blocking-contracts.md`. Private partner/staff responses use `Cache-Control: private, no-store`. Validation errors use the shared `{message,code,requestId}` envelope. A version conflict requires reloading the returned resource before a new challenge and mutation.

Partner kinds: `inspection_partner`, `legal_partner`, `engineering_survey_partner`, `valuation_partner`, `buyers_agent`, `sellers_agent`. The service-key vocabulary is `src/constants/partnerServices.js`; specialty keys are `src/constants/partnerCredentials.js`. Mortgage is reserved and not exposed.

## Public profile, directory and following

`PublicReview` is `{id,rating,comment,createdAt,reply,version}`; `reply` is null or `{text,createdAt}`. Reviewer identity, transaction, payment, email, phone and reply-author identity are not projected. The minimum two qualifying reviews rule applies to `average`; below that it is null. Legacy seller reviews without `sellerProfile` appear only if their completed escrow identifies this exact seller profile; current property ownership is never used as a substitute. Replies require the exact review `version` and return `409 CONFLICT_PROFILE_REVIEW_VERSION` or `CONFLICT_PROFILE_REVIEW_ALREADY_REPLIED` on stale/duplicate requests. Invalid cursor/query returns `400 INPUT_PROFILE_REVIEW_QUERY_INVALID`; invalid reply returns `422 INPUT_PROFILE_REVIEW_REPLY_INVALID`; off-platform contacts remain blocked. `POST` responses are private/no-store. Account-follow actions and followed-listing search require the registered email-verification level, not phone verification. A current public seller/partner profile can be followed; only buyer profiles require the separate `followable=true` opt-in. Follower names omit buyers who did not opt in.

Public seller and partner review lists recheck the same current paid/completed, ownership/profile and non-refund evidence used for the displayed rating. A review whose sale or service job is refunded, disputed or otherwise no longer eligible is not returned, and its author can no longer add a reply through this profile route. A public profile's qualifying review average remains available after two source-backed reviews even if `profile_trust_scoring` is unconfigured; trust score/tier remains independently unavailable until its approved policy is active. Cursor ordering remains descending review ID. No rating is synthesized from legacy account counters for a profile with no qualifying source records.

Video autoplay is an identity-wide Settings choice across profiles. The existing `GET /api/auth/account` and authenticated login account DTO now include `preferences:{videoAutoplay:"always"|"wifi_only"|"never"}`. The source default is `wifi_only`, including for legacy accounts without a stored preference. `PATCH /api/auth/account/preferences` requires Bearer authentication and JSON `{ "videoAutoplay": "never" }`, returns `200 { "preferences": { "videoAutoplay": "never" } }`, and rejects unknown fields or values with `422 INPUT_ACCOUNT_PREFERENCES_INVALID`. The write rechecks the current account session and returns `409 CONFLICT_IDENTITY_AUTHORIZATION` if it changes during the mutation. This preference is never included in public profile/user DTOs. Both account reads and preference writes use private/no-store caching; no selected profile or step-up is required for this identity-level presentation choice. The frontend still enforces Wi-Fi detection, muted playback, one loop and viewport visibility locally; this setting does not start a server video stream.

Public profile core fields are `profileId`, `kind`, `structure`, `roleLabel`, `name`, `memberSince`, `profileImageUrl`, `verified`, `verifiedAt`, `trust`, `rating`, `counts:{followers,following}`, plus `body` as defined below. A buyer profile remains private by default and may opt into its minimal followable page; its trust and rating stay hidden. For seller/partner profiles with an approved `profile_trust_scoring` and `trust_tier_thresholds` revision and enough current evidence, `trust` includes `state`, `tier`, `score`, `components`, `sourceCounts`, and `policyRevisions`. `state` is `new|established|unavailable`; unavailable scores/components are null. Average rating remains null until two qualifying reviews. No raw KYC, contact data, dispute narrative or private case is public.

`body` is `null` for buyer and partner core pages (the richer partner page is `/api/partners/profiles/:profileId`). For an individual owner it is `{kind:"owner",state:"ready"|"unavailable",listings:[PublicProperty],unavailableCode?}`. For an agency it also contains `team:[{name,role}],managedListings:[PublicProperty],managedListingsState:"ready"|"unavailable",managedListingsUnavailableCode?`; for a developer it also contains `projects:[{id,name,slug,projectType,status,location,coverImage,publishedAt,handoverSchedule}],projectsState:"ready"|"unavailable",projectsUnavailableCode?`. `handoverSchedule` is `{originalMonth:string|null,currentMonth:string|null,revised:boolean|null,historyAvailable:boolean}`. Only a project created after schedule provenance began can claim an original month; a legacy project with no verified original returns `originalMonth:null`, `revised:null`, `historyAvailable:false`. This shows projected months, never a claim of actual handover. `listings` is a capped preview (up to 12) of current canonical catalogue results for this exact owner profile, rechecked through the shared search pipeline; it is not a total count. Agency `managedListings` is another capped preview, requiring an accepted, unexpired property or project mandate with `listing.read`; no agency relationship is inferred from a shared account or unapproved agent label. Project cards require current publication and at least one currently eligible child unit; suspended/unclassified projects remain hidden. Agency team names and roles come only from active, entitled seats with current account status. No team contact, seat, performance or payout field is returned. A catalogue feature-policy gate yields an unavailable state and empty previews; it never substitutes stale listings. Actual developer handover performance remains unavailable until a signed handover event is captured.

Project follows are separate from account follows. Both feed the existing `followingOnly` catalogue/search scope, including saved-search matching under the same selected profile. The server rechecks current project publication and eligible child units before a follow; unpublished projects are hidden from the followed-project list. A follow never grants private project access. Errors: `400 CONTENT_PROJECT_FOLLOW_QUERY_INVALID`, `400 INPUT_PROJECT_ID_INVALID`, `404 CONTENT_PROJECT_FOLLOW_UNAVAILABLE`, `409 CONFLICT_PROJECT_FOLLOW_CHANGED`, plus existing profile/session/policy errors. Private follow responses use `Cache-Control: private, no-store`. Project-follow metadata is included in the profile data-rights export and eligible deletion plan; legal holds and retention apply.

`FollowingFeedItem` is `{id,kind:"new_listing"|"price_change"|"project_progress"|"open_house"|"show_home"|"social_post",occurredAt,property:PublicProperty,projectId?,milestone?,milestonePhase?,progressPercentage?,title?,changeType?}`. `project_progress` supplies its current project ID, source-defined construction milestone/phase and safe update title; `price_change` supplies `changeType:"increase"|"decrease"|"currency_change"`, never private history, reserve or sale amounts. The feed combines new listings by followed public profiles or followed projects, dated construction updates on followed projects, and asking-price events for matching listings. It sorts newest first with a stable kind/ID tie-breaker. It rechecks account/profile/seat authority and follow visibility, then uses the current canonical catalogue for every candidate listing, so withdrawn, unpublished or ineligible properties cannot leak from historical events. A sparse or empty page can still have `nextCursor` while older source events remain; pass it back unchanged. Invalid query/cursor returns `400 CONTENT_FOLLOWING_FEED_QUERY_INVALID`; a catalogue configuration gate returns its existing safe `503 FEATURE_*` error. Open-house and show-home events recheck their current schedule digest and canonical publication; social-post items carry a current public post DTO instead of a property.

New project creation records the first source-defined `canonicalFields.projectedHandoverMonth` (format `YYYY-MM`) as its original schedule. `PATCH /api/projects/:id` may send `canonicalFieldMutations:[{field:"projectedHandoverMonth",operation:"set",value:"2030-09"}]` with `expectedVersion` and optional `handoverRevisionReason` (1–1000 characters, on-platform text). The reason is accepted only when that canonical month changes. The authorized project detail response adds `handoverSchedule` with the same public-safe shape; revision provenance remains in the stored project audit/history. A pre-existing project's first observed month is a legacy baseline, not a fabricated original. Errors include `422 CONTENT_PROJECT_HANDOVER_REASON_INVALID` and the existing canonical month/version errors. Changing a projected month does not establish a signed actual handover or a trust performance count. A developer trust policy revision must explicitly include the `handoverRecord` component; an older revision omitting it yields `FEATURE_PROFILE_TRUST_POLICY_REVISION_REQUIRED`. A positive approved weight for this component keeps the score unavailable until signed actual handover evidence exists. No construction-completion timestamp is substituted.

Buyer trust is relationship-only. The selected seller must hold `enquiry.read`, or the selected partner `partner.jobs.read`; an assigned-only seat cannot use an unscoped relationship read. The backend checks exact buyer and viewer profile IDs against on-platform Inquiry, Tour, Escrow or PartnerJob records, then rechecks active buyer identity/profile. A stranger receives `404 CONTENT_BUYER_TRUST_NOT_AVAILABLE`. The private `trust` DTO is `{state,tier,score,components,sourceCounts,rating,policyRevisions,unavailableCode?,unavailableSignals?}` and omits appeal/fingerprint fields. Buyer transactions come from released buyer-profile escrows and adverse disputes from independently resolved buyer-fault escrow cases. Buyer ratings are reciprocal, private numeric ratings from completed, non-refunded profile-bound sales or paid partner jobs; the scorer rechecks those source states before counting a stored rating. Buyer responsiveness uses the first on-platform buyer reply after a seller/partner message in a conversation bound to both exact profiles; unanswered opportunities lower the component, and a source without an incoming message creates no response opportunity. New messages persist the selected sender profile; older messages count only when their sender is the exact profile holder. An approved `profile_trust_scoring` buyer rule and tier policy are required for established scores. A positive weight with no qualifying rating or response evidence leaves the score unavailable rather than inventing a score.

`POST /api/trust/v1/profile/:profileId/relationship/reviews` records one buyer rating for a completed source relationship. Bearer authentication and `X-Profile-ID` select the current verified owner/agency/developer or partner profile. Only the holder's active owner seat may write; it needs `enquiry.read` for an escrow or `partner.jobs.read` for a partner job. `:profileId` is the actual buyer profile ID. Body is exactly `{ "sourceKind":"escrow"|"partner_job", "sourceId":"<ObjectId>", "rating":1..5 }` with an integer rating. A sale must be released, profile-bound to this buyer and seller, and not refunded. A partner job must be completed, paid, not refunded, and bound to the buyer/client and selected partner profile. `201 {review:{id,buyerProfileId,reviewerProfileId,sourceKind,sourceId,rating,createdAt},changed:true}` is returned on creation; an exact repeat returns `200` with the same `review` and `changed:false`. A different rating for that source returns `409 CONFLICT_BUYER_REVIEW_EXISTS`; the rating is immutable. Invalid body returns `422 INPUT_BUYER_RELATIONSHIP_REVIEW_INVALID`; unrelated, unfinished or refunded source returns `403 CONTENT_BUYER_REVIEW_RELATIONSHIP_REQUIRED`; wrong profile/seat returns `403 PERMISSION_BUYER_REVIEW_REQUIRED`; expired reviewer verification returns `403 KYC_PROFILE_VERIFICATION_REQUIRED`. The response is private/no-store. No reviewer name, comment, contact or individual rating is added to the public buyer page. The related-party trust view exposes only the aggregate and qualifying count.

`GET /api/properties?sort=trust_tier|highest_rated` and the same canonical map/group search use the listing's current seller profile for ranking whenever `ownerProfile` is present. Trust Tier uses that exact profile's current approved role-specific trust score and tier, including genuine `new` status; Highest Rated uses only buyer reviews attached to that seller profile whose paid, fulfilled, owned and non-refunded sale evidence remains current. A single account's other seller profiles cannot supply the ranking value. Legacy listings without an owner profile retain the account-level trust/review ranking path. Unavailable trust signals do not become a synthetic score; rows without a current tier or at least two qualifying ratings sort after ranked rows, then by canonical newest and stable ID. `trust_tier` needs approved `profile_trust_scoring` and `trust_tier_thresholds` for profile-associated rows and returns `503 FEATURE_SEARCH_TRUST_TIER_POLICY_UNCONFIGURED` when absent. Recommended tie-breaking remains governed by the existing `recommended_weights` policy and its deterministic newest fallback. No private trust components, reviewer identities or source payment records enter catalogue/map/group responses.

Directory `partners[]` is one currently approved service card per matching offering: `{profileId,name,kind,roleLabel,structure,verified,profileImageUrl,trust,rating,service,serviceAreas,availability}`. `service` is the approved offering DTO below, including `bookable` and `unavailableCode`; `serviceAreas[]` contains `{stateId,name}` and `serviceAreaCities[]` contains `{cityId,stateId,name}` from the current approved revision. Cursor is the last scanned offering ID, descending; live eligibility and trust filtering may make a page sparse. An empty array with `state:"ready"` is a real empty page. If the service policy is missing: `200 {state:"unavailable",code:"FEATURE_POLICY_UNCONFIGURED",partners:[],nextCursor:null}`. `cityId` is an exact current approved city ID. It returns `503 FEATURE_PARTNER_CITY_DATA_UNAVAILABLE` until an approved gazetteer revision contains authoritative city entries. Cities are state children and are never inferred from an LGA or area label. A trust filter without approved scoring/tier policies returns `503 FEATURE_PROFILE_TRUST_POLICY_UNCONFIGURED`. An invalid or stale state ID returns the gazetteer validation error. Unavailable/suspended providers are never bookable. A service whose sole dependent professional credential expired stays on the public page with `bookable:false` and `unavailableCode:"KYC_PARTNER_SERVICE_CREDENTIAL_EXPIRED"`.

Public partner `services[]` use `{id,profileId,kind,serviceKey,label,observational,currency,rateMinor,turnaroundHours,paymentTerm,state,version,bookable,unavailableCode,credentialKinds,credentialExpiresAt,specialties,serviceAreaStateIds,serviceAreaCityIds,serviceAreas,serviceAreaCities,approvedAt,updatedAt}`. Observational proxy visits and handover attendance must show “Observational visit, not a technical inspection”. `credentials[]` contains only `{kind,label,issuerName,verifiedAt,expiresAt,status:"current"|"expired"}` from approved review, never the evidence ID or private reference. `indemnityInsurance` is `{held:false}` or `{held:true,status,issuerName,verifiedAt,expiresAt}`. An issuer not recorded in an older review is `null`; do not fabricate it.

The existing notification centre now receives on-platform `category:"followed_updates"` notices with `type:"following.new_listing"|"following.price_change"|"following.project_progress"|"following.open_house"|"following.show_home"|"following.social_post"` for eligible current followed listings. Each notice carries a safe property route and no price, private terms, contact or provider details. The worker rechecks the current follower account/profile/seat and source follow, target visibility, and canonical public listing before sending. Notification preferences may archive the in-app notice. Email, SMS, WhatsApp and push are not requested for these follower updates. Profile and project follows share an idempotency key per follower profile/source event, so following both does not double-notify. A persisted event cursor advances only after an eligible notice is saved or an ineligible source event is skipped; failures keep the event for retry. Existing follows predating this worker initialize at activation without replaying old history. `FOLLOWING_NOTIFICATION_SCHEDULER_ENABLED=false` pauses delivery; polling interval and per-source scan bound reuse `MARKETPLACE_ALERT_SCHEDULER_INTERVAL_MS` and `SEARCH_ALERT_MAX_EVENTS_PER_BATCH`. The existing notification APIs and socket event provide the frontend delivery contract; there is no new follower-notification endpoint. Deployment must build the profile/project follow notification-scan indexes.

## Project questions and moderated developer answers

Project questions are separate from developer-profile reviews. The existing `/api/projects` router mounts these routes. Every answer and question starts private in `pending`; no pending or rejected content is placed on the public project page. This is a manual Trust & Safety moderation flow, and a submission never implies publication.

| Method/path | Request | Success | Access |
|---|---|---|---|
| `GET /api/projects/:idOrSlug/questions?after=<ObjectId>&limit=25` | Project ID or slug; `limit` 1–100; descending question cursor | `200 {questions:[{id,projectId,question,answer,createdAt}],nextCursor}`; `answer` null until separately approved | Guest; current published project with eligible units |
| `POST /api/projects/:idOrSlug/questions` | JSON `{question:string}`; nonempty, <=2,000 characters, on-platform content | `201 {question:{id,projectId,question,answer:null,createdAt,state:"pending",version:0,answerState:"none"}}` | Signed-in selected non-staff profile; private/no-store |
| `GET /api/projects/:idOrSlug/questions/manage?after=<ObjectId>&limit=25` | Same bounded cursor | `200 {questions:[PrivateQuestion],nextCursor}` | Current owning developer profile, `project.edit`; private/no-store |
| `PATCH /api/projects/:idOrSlug/questions/:questionId/answer` | JSON `{answer:string,expectedVersion:integer}`; same text rule | `200 {question:PrivateQuestion}` with `answerState:"pending"`, `pendingAnswer` and incremented `version` | Current owning developer profile, `project.edit`; private/no-store; rejected answers may be revised, prior versions retained privately |
| `GET /api/admin/project-questions?after=<ObjectId>&limit=25` | Same bounded cursor | `200 {questions:[PrivateQuestion],nextCursor}`; pending questions or answers only | Current Trust & Safety staff profile; private/no-store |
| `PATCH /api/admin/project-questions/:id/moderation` | Bound step-up; JSON `{target:"question"|"answer",decision:"approve"|"reject",expectedVersion:integer,reason:string}`; reason nonempty, <=1,000 characters | `200 {question:PrivateQuestion}` with updated state/version | Current Trust & Safety staff profile, independent of author; private/no-store |

`PrivateQuestion` is `{id,projectId,question,answer,createdAt,state:"pending"|"approved"|"rejected",version,answerState:"none"|"pending"|"approved"|"rejected",pendingAnswer?}`. The public DTO never includes author identity, profile IDs, moderation reasons or pending answers. `answer` is `{text,answeredAt}` only after independent approval. The question author is not projected to the developer or public. Staff moderation rechecks current author identity/profile, developer ownership for an answer, the published project and off-platform contact restrictions before approval. `reviewReason` and rejected answer history remain private; audit records the decision and version. Errors include `400 INPUT_PROJECT_ID_INVALID|INPUT_PROJECT_QUESTION_QUERY_INVALID`, `422 INPUT_PROJECT_QUESTION_INVALID|INPUT_PROJECT_ANSWER_INVALID|INPUT_PROJECT_QUESTION_DECISION_INVALID`, `403 PERMISSION_PROJECT_ANSWER_REQUIRED|PERMISSION_STAFF_PROFILE_REQUIRED|PERMISSION_DEPARTMENT_REQUIRED|PERMISSION_SEPARATION_OF_DUTIES`, `404 RESOURCE_NOT_FOUND|CONTENT_PROJECT_FOLLOW_UNAVAILABLE`, and `409 CONFLICT_PROJECT_QUESTION_VERSION|CONFLICT_PROJECT_ANSWER_STATE|CONFLICT_PROJECT_QUESTION_AUTHOR_UNAVAILABLE|CONFLICT_PROJECT_ANSWER_AUTHOR_UNAVAILABLE`. An invalid step-up follows the shared auth error contract. On 409, reload the question and bind a new challenge if moderating.

Project questions authored by a selected profile are included in the private data-access export and, after the approved `support_record` retention/grace period, in the deletion plan. Pending or rejected unanswered questions are deleted; approved/answered questions are anonymized and removed from public results while a developer's separately authored answer is retained in the protected record. Current legal holds and execution authority are rechecked before each action. Developer-authored answers and review replies are separately attributed to their actual submitting identity and selected profile; eligible response text and matching answer history can be redacted without deleting another person’s question or review. Their active or historical response is included in that author’s private data-access export. An answer/reply cannot be approved by its own submitting identity.

## Separate project reviews and category ratings

Project reviews never enter developer-profile review averages. A verified buyer profile can review a current public project using a source-bound released purchase, completed on-platform viewing or initialized property checkout for one of that project's units. Page views, favourites, inquiries alone and uninitialized payment reservations do not qualify. Submitted reviews and developer replies are held until independent Trust & Safety moderation. Public reads recheck the recorded source relationship, buyer identity/profile eligibility and the unit's current project relationship; stale, refunded, revoked or unrelated evidence cannot supply a public review or rating.

| Method/path | Request | Success | Access |
|---|---|---|---|
| `GET /api/projects/:idOrSlug/reviews?after=<ObjectId>&limit=25` | Project ID or slug; `limit` 1–100 (default 25), descending review cursor | `200 {reviews:[PublicProjectReview],nextCursor,summary:{qualifyingReviewCount,categoryAverages}}` | Guest; only current public project with eligible units |
| `GET /api/projects/:idOrSlug/reviews/mine` | Project ID or slug; no query | `200 {review:PrivateProjectReview|null}` including pending/rejected state | Signed-in selected buyer profile, `dashboard.read`; private/no-store; can read an unpublished historical project review |
| `POST /api/projects/:idOrSlug/reviews` | JSON `{propertyId:ObjectId,sourceKind:"purchase"|"viewing"|"checkout",sourceId:ObjectId,ratings:{communication:1..5,documentation:1..5,paymentHandling:1..5},comment:string}` | `201 {review:PrivateProjectReview}` with `state:"pending",version:0` | Current verified buyer profile; `dashboard.read`; private/no-store |
| `PATCH /api/projects/:idOrSlug/reviews/:reviewId/reply` | JSON `{text:string,expectedVersion:integer}` | `200 {review:PrivateProjectReview}` with `replyState:"pending"` | Current owning developer, `project.edit`; one reply only; private/no-store |
| `GET /api/admin/project-reviews?after=<ObjectId>&limit=25` | Same bounded cursor | `200 {reviews:[PrivateProjectReview],nextCursor}` for pending reviews/replies | Current Trust & Safety staff profile; private/no-store |
| `PATCH /api/admin/project-reviews/:id/moderation` | Bound step-up; JSON `{target:"review"|"reply",decision:"approve"|"reject",expectedVersion:integer,reason:string}` | `200 {review:PrivateProjectReview}` | Independent Trust & Safety staff reviewer; private/no-store |

`PublicProjectReview` is `{id,projectId,badge:"verified_buyer"|"verified_enquirer",ratings:{communication,documentation,paymentHandling},postHandoverRatings:{buildQuality,finishing,promiseMatch}|null,comment,createdAt,reply,version}`. `reply` is `null` until separately approved, then `{text,repliedAt}`. `PrivateProjectReview` additionally has `state:"pending"|"approved"|"rejected",replyState:"none"|"pending"|"approved"|"rejected",pendingReply?`. Public and developer DTOs omit buyer name, account/profile ID, source ID, moderation reason, contact details and private transaction information. Public `summary.categoryAverages` is `null` until at least two still-qualifying reviews; otherwise it contains an average for each of the three supported pre-handover categories. `postHandoverCategoryAverages` is null until two still-qualifying signed handover reviews exist. No combined overall score is fabricated. `sourceKind:"purchase"` uses a released, non-refunded escrow with a paid fulfilled property purchase and owned record; `viewing` uses a completed non-partner viewing; `checkout` uses a server-initialized property purchase payment. `sourceId` is the ID of that escrow, tour or payment, respectively. The backend verifies the exact selected buyer profile, identity, project and unit. The buyer can submit once per project; a source cannot be changed through a public endpoint. Review and reply text must be nonempty, at most 2,000 characters and on-platform. Staff reason is nonempty and at most 1,000 characters.

Example submit: `POST /api/projects/<projectId>/reviews` with `Authorization`, `X-Profile-ID` and body `{"propertyId":"<unit ObjectId>","sourceKind":"viewing","sourceId":"<completed tour ObjectId>","ratings":{"communication":5,"documentation":4,"paymentHandling":4},"comment":"The viewing and documents were clear."}`. The response is `201 {"review":{"id":"<review ObjectId>","projectId":"<project ObjectId>","badge":"verified_enquirer","ratings":{"communication":5,"documentation":4,"paymentHandling":4},"comment":"The viewing and documents were clear.","createdAt":"<ISO timestamp>","reply":null,"version":0,"state":"pending","replyState":"none"}}`. These placeholders are identifiers, not values to submit literally.

Errors: `400 INPUT_PROJECT_ID_INVALID|INPUT_PROJECT_REVIEW_QUERY_INVALID`; `422 INPUT_PROJECT_REVIEW_INVALID|INPUT_PROJECT_REVIEW_REPLY_INVALID|INPUT_PROJECT_REVIEW_DECISION_INVALID|CONTENT_OFF_PLATFORM_CONTACT_BLOCKED`; `403 KYC_PROJECT_REVIEW_REQUIRED|CONTENT_PROJECT_REVIEW_RELATIONSHIP_REQUIRED|PERMISSION_PROJECT_REVIEW_REQUIRED|PERMISSION_PROJECT_REVIEW_REPLY_REQUIRED|PERMISSION_STAFF_PROFILE_REQUIRED|PERMISSION_SEPARATION_OF_DUTIES`; `404 RESOURCE_NOT_FOUND|CONTENT_PROJECT_FOLLOW_UNAVAILABLE`; `409 CONFLICT_PROJECT_REVIEW_EXISTS|CONFLICT_PROJECT_REVIEW_VERSION|CONFLICT_PROJECT_REVIEW_AUTHOR_UNAVAILABLE|CONFLICT_PROJECT_REVIEW_SOURCE_UNAVAILABLE|CONFLICT_PROJECT_REVIEW_REPLY_AUTHOR_UNAVAILABLE`. A stale version requires reloading and a new bound challenge for staff moderation. Post-handover build-quality, finishing and promise-match categories require a signed actual unit handover record; no projected month or construction update qualifies. No combined overall project score is inferred. Approved reviews are included in the private data-access export and governed by approved support-record retention, legal holds and anonymization; anonymized reviews leave public results and category averages. The report may be resubmitted with a newly issued document after staff rejection. The acceptance window is locked from approved `partner_service_terms.reportAcceptanceHours` when the job is offered. A bounded worker accepts a current sealed on-acceptance report after that window, preserving the hold if the partner is suspended or the document is stale. A stale report is moved to `report_review_required` for staff correction, never autoaccepted.

For a partner live guided video job, request the `inspection_partner:live_guided_video_tour` service with a current published `propertyId`, confirm the due-now payment or choose the approved on-completion term, then schedule a future partner calendar slot. The client receives a participant join link; the partner receives the host link only from the no-store join route. No seller-property route can mutate a job-bound session. The ordinary `/api/tour` list excludes partner jobs; partner appointments do not occupy the property's seller-calendar availability or receive legacy paid-tour credits. Revocation or an expired appointment ends access; the worker removes the Zoom meeting at expiry. Missing Zoom credentials return `503 FEATURE_LIVE_VIDEO_PROVIDER_UNAVAILABLE`; scheduler/provider unavailable returns the existing `LIVE_VIDEO_*` readiness code; unpaid booking returns `409 CONFLICT_PARTNER_VIDEO_PAYMENT_REQUIRED`; absent property returns `422 INPUT_PARTNER_VIDEO_PROPERTY_REQUIRED`. Provider absence returns a feature/configuration error before a payment reservation. The payment callback rechecks current payer seat and exact locked amount, currency, provider reference and segregated account.

An unresolved paid-service dispute blocks new charges, report acceptance, automatic acceptance and new beneficiary transfers. A client opens one with the job's current version and a unique operation key; a repeated identical operation key returns the existing case. `ParticipantDisputeDTO` is `{id,jobId,state,version,decision,decidedAt,resolvedAt,createdAt,updatedAt}`. The requesting client and assigned partner see these safe state fields; reasons are withheld. `StaffDisputeDTO` adds `{clientProfileId,partnerProfileId,reason,decisionReason,upheldAgainstPartner}` for the authorized Third-Party Network queue. `pay` requires the current sealed report, accepts it and releases the dispute hold without initiating settlement; Finance must separately release. `redo` returns the report to the correction workflow and releases the dispute hold. `refund` records an upheld, unresolved refund decision and **keeps the hold** until Finance executes and reconciles the full amount actually collected. A completed settlement requires a separate, provider-confirmed partner recovery collection before Finance can refund the buyer; see the recovery contract below. Errors include `409 CONFLICT_PARTNER_DISPUTE_ACTIVE|CONFLICT_PARTNER_DISPUTE_VERSION|CONFLICT_PARTNER_DISPUTE_NOT_ELIGIBLE`, `422 INPUT_PARTNER_DISPUTE_INVALID|INPUT_PARTNER_DISPUTE_DECISION_INVALID`, and ordinary bound step-up errors.

`PartnerRefundDTO` is `{id,jobId,disputeId,state,version,amountMinor,currency,reference,destinationMasked,destinationBankName,providerState,checkedAt,completedAt,lastFailureCode,actionEligibility:{initiate,authorize,reconcile},createdAt,updatedAt}`. States are `ready`, `initiating`, `pending_authorization`, `processing`, `completed`, `reconciliation_required`. `prepare` returns an existing reservation on safe retry, requires no pending collection and exact provider-confirmed custody **whose partner-job fulfillment has completed**, and aborts only an unstarted settlement reservation. The preparing Finance identity cannot initiate or authorize the refund (`403 PERMISSION_SEPARATION_OF_DUTIES`). `initiate`/`authorize` claim one original transfer reference; an ambiguous provider outcome becomes `reconciliation_required` and must be checked with `/reconcile`, never initiated again blindly. A `SUCCESS` without exact amount and currency remains in reconciliation. Only provider-confirmed completion marks job payment `refunded`, job `cancelled` and dispute `resolved`; payment records remain as immutable original collection evidence. A Finance operator sees only masked destination fields. Configuration, custody and version errors include `503 FEATURE_MONNIFY_ESCROW_UNCONFIGURED|FEATURE_MONNIFY_ESCROW_DISBURSEMENT_UNAVAILABLE|FEATURE_FINANCIAL_LIMIT_EXCEEDED`, `409 CONFLICT_PARTNER_CUSTODY_UNCONFIRMED|CONFLICT_PARTNER_FUNDS_ALREADY_IN_TRANSFER|CONFLICT_PARTNER_REFUND_VERSION|CONFLICT_PARTNER_PAYMENT_PENDING`, and `422 INPUT_PARTNER_REFUND_INVALID`.

No legacy identity ID is guessed when the profile association is missing. The scorer sums the approved default or case override for each currently eligible case, respecting the approved decay period and capping the dispute component at zero. Invalid input returns `400 INPUT_PROFILE_TRUST_DISPUTE_INVALID` or `422 INPUT_PROFILE_TRUST_IMPACT_INVALID`; a missing case returns `404 RESOURCE_NOT_FOUND`; an unlinked legacy case returns `409 CONFLICT_PROFILE_TRUST_DISPUTE_UNLINKED`; a stale adjustment returns `409 CONFLICT_PROFILE_TRUST_IMPACT_VERSION`; absent approved role scoring returns `503 FEATURE_POLICY_UNCONFIGURED|FEATURE_PROFILE_TRUST_POLICY_UNCONFIGURED`. The mutation reason and history remain staff-only. Example protected request after bound step-up: `PATCH /api/trust/v1/admin/disputes/escrow/<disputeId>/impact` with `X-Profile-ID:<staffProfileId>`, `X-Step-Up-Challenge:<verified challenge>` and JSON `{ "expectedVersion": 0, "penaltyPoints": 8, "reason": "Reviewed upheld case evidence" }`. The number is an example of a staff decision, not a default or approved threshold.

Policy `partner_service_terms` is owned by Third-Party Network and `profile_trust_scoring` by Trust & Safety through existing versioned Console policy endpoints (`GET /api/admin/policies/:key`, revision preparation/approval routes). Both require approved values. The partner terms policy covers every `kind:serviceKey`, current specialty set, allowed payment terms, optional deposit percentage, minimum paid completed jobs for unlocked terms, report acceptance hours, About word limit and matching candidate bound. Trust policy supplies role-specific signal weights totalling 100, `minimumCompleted`, `minimumQualifyingReviews`, transaction target count, response/turnaround target hours, dispute penalty points, `disputeDecayDays` and title target count. `disputeDecayDays` must be an explicitly approved integer from 1 to 36500 or `null` for no decay. An older approved role rule lacking that decision returns `FEATURE_PROFILE_TRUST_DISPUTE_POLICY_UNCONFIGURED` when disputes carry positive weight; no decay is inferred. Weighting an unavailable signal does not create a score.

## Stable error and recovery examples

- `400 INPUT_PARTNER_DIRECTORY_QUERY_INVALID`, `INPUT_PARTNER_JOB_QUERY_INVALID`, `INPUT_PARTNER_EARNINGS_QUERY_INVALID`: correct query and cursor.
- `403 PERMISSION_PARTNER_PROFILE_REQUIRED`, `KYC_PARTNER_VERIFICATION_REQUIRED`, `PERMISSION_SEPARATION_OF_DUTIES`: select the authorized current profile or seek review; do not retry under another identity.
- `409 CONFLICT_PARTNER_SERVICE_VERSION`, `CONFLICT_PARTNER_JOB_VERSION`, `CONFLICT_PARTNER_REPORT_VERSION`, `CONFLICT_PARTNER_REPORT_DOCUMENT_STALE`, `CONFLICT_PARTNER_SETTLEMENT_VERSION`: reload the current DTO and bind a fresh step-up challenge.
- `503 FEATURE_POLICY_UNCONFIGURED`, `FEATURE_PARTNER_CREDENTIAL_POLICY_EXPIRED`, `FEATURE_PARTNER_CURRENCY_UNAVAILABLE`, `FEATURE_PARTNER_CITY_DATA_UNAVAILABLE`, `FEATURE_PROFILE_TRUST_POLICY_UNCONFIGURED`: show a safe unavailable state; never substitute client-supplied eligibility, price or trust data.
- `403 AUTH_STEP_UP_REQUIRED`, `AUTH_STEP_UP_INVALID` or one-use challenge errors: initiate and verify a new challenge for the exact protected request.

For bid-funded campaigns, the approved bid is debited on the configured `click` or `enquiry` event and cannot exceed prepaid balance. A billable click must come from the same selected buyer profile that received the impression; `SOCIAL_PROMOTION_CHARGE_DEDUP_SECONDS` prevents repeat click charges from that profile within its configured window. The server ranks eligible sponsored candidates by approved bid/quality weights and stable start-time/ID ties. If the completeness policy is unavailable and quality has nonzero weight, all weighted paid products are unavailable. Paid placements have no effect on automatic partner assignment or organic feed ranking.

Checkout and recovery: follow only the `payment.checkoutUrl` returned for the original campaign; call the existing authenticated `GET /api/payments/verify/:reference` using that same reference after Paystack returns, then reload campaign detail. `payment.reconciliationRequired:true` means do not open a new checkout. A `pending_payment` campaign cannot serve. The revenue recovery scheduler resumes paid activation, pauses expired or ineligible campaigns, reconciles product refunds and issues pending fiscal documents. A paid campaign paused before its first activation begins its approved duration only when current policy and target eligibility allow activation. Its locked tax rate comes from the original approved tax quote, even when minor-unit rounding makes the tax amount zero. The seller can end an active or paused paid campaign; an independently approved Finance refund may be required by existing financial execution thresholds. Finance uses existing `GET /api/admin/revenue/product-refunds`, `POST /api/admin/revenue/product-refunds/:id/decision` with `{decision:"approve"|"reject",reason,expectedVersion}`, and `POST /api/admin/revenue/product-refunds/reconcile`. `ProductRefundDTO` for this product has `productKind:"social_promotion"`, `sourceType:"social_promotion"`, `sourceId` equal to the original funding campaign ID (which may differ after a direct transfer), amounts, state, providerStatus, providerRefundReference, creditNoteId, events and version. Provider outcome unknown and credit-note pending states require same-reference reconciliation; never blindly repeat a refund. Common errors include `422 INPUT_SOCIAL_PROMOTION_INVALID|INPUT_SOCIAL_PROMOTION_BUDGET_INVALID|INPUT_SOCIAL_PROMOTION_END_INVALID`, `403 PERMISSION_*|AUTH_STEP_UP_REQUIRED`, `409 CONTENT_SOCIAL_PROMOTION_TARGET_INELIGIBLE|CONTENT_SOCIAL_PROMOTION_LISTING_INELIGIBLE|CONFLICT_SOCIAL_PROMOTION_VERSION|CONFLICT_SOCIAL_PROMOTION_OPERATION`, and `503 FEATURE_SOCIAL_PROMOTION_POLICY_UNCONFIGURED|FEATURE_SOCIAL_PROMOTION_QUALITY_UNCONFIGURED|FEATURE_PAYSTACK_UNCONFIGURED|FEATURE_REVENUE_TAX_UNCONFIGURED`.

### Audience, organic comparison and direct next-campaign transfer

Campaign creation accepts an optional audience object with only areaId, priceBand, buyerType, residence and buyerCountry. areaId is an ObjectId for an Area in the current approved gazetteer revision; priceBand is one of under_25m, 25m_50m, 50m_100m, 100m_250m, 250m_500m, 500m_1b, over_1b from the canonical NGN catalogue; buyerType is individual, company or cooperative; residence is local or abroad; buyerCountry is an uppercase ISO two-letter country code. All supplied controls must match. A campaign with no audience remains broadly eligible. Area and price-band targeting require a current canonical-v1 saved search on the selected buyer profile containing that exact area ID and/or price band. Country and local/abroad targeting use the currently approved individual buyer verification case of the account, never a client-supplied country. Buyer type uses the selected buyer profile structure. Guests and profiles without authoritative matching data do not receive targeted placements. An area revision change pauses that campaign until its audience is revised in a new campaign; it cannot silently use a different geographic ID. Errors include 422 INPUT_SOCIAL_PROMOTION_AUDIENCE_INVALID and 409 CONTENT_SOCIAL_PROMOTION_AREA_INVALID; missing approved gazetteer data returns 503 FEATURE_SEARCH_GAZETTEER_UNCONFIGURED.

`AudienceOptionsDTO` is `{area:{level:"area",suggestionsPath:"/api/locations/suggestions",requiredParentLevel:"lga",valueField:"id"},priceBands:["under_25m","25m_50m","50m_100m","100m_250m","250m_500m","500m_1b","over_1b"],buyerTypes:["individual","company","cooperative"],residences:["local","abroad"],buyerCountry:{format:"ISO-3166-1-alpha-2-uppercase"}}`. For an area selection use `GET /api/locations/suggestions?level=area&parentId=<current-lga-id>&q=<2–80-character-prefix>&limit=10` (limit 1–20) and submit the returned `suggestions[].id`; an unconfigured gazetteer yields `503 FEATURE_SEARCH_GAZETTEER_UNCONFIGURED`. The campaign catalogue returns these supported controls even when the promotion product policy is unavailable, without implying that a purchase can proceed.

Campaign detail adds organicComparison: {state,period,impressions,definition?}. State is not_started, telemetry_unavailable, partial_window or ready. Period is null before activation or {from,to} in ISO timestamps. Impressions is {sponsored,organic}; organic is null when telemetry is unavailable. The comparison counts server-served organic cards for the same post or partner profile during the campaign window, and the existing sponsored impression events for the campaign. It does not claim viewport attention, unique people or an organic enquiry attribution. Organic cards are instrumented on public post list, profile-post list, Explore and partner directory reads; editorial Featured and paid Sponsored responses are excluded. Tracking begins when the new organic telemetry head first records a read; older campaigns show partial_window instead of a fabricated complete baseline. Post/partner detail reads are separately tracked for future diagnostics but are not counted as card impressions. The response is private/no-store and contains no viewer identities.

POST /api/posts/promotions/:id/end retains the existing body {expectedVersion,operationKey} as a refund request. It also accepts disposition:"refund" explicitly. To move unused value directly into the next campaign, send disposition:"transfer" and nextCampaign:{targetKind,targetId,productId,currency,bidMinor?,audience?} with the same bound step-up. The server derives the unused net and proportional locked VAT from the source campaign. The next campaign must belong to the same currently authorized advertiser and use the same original currency. The transferred amount retains the original approved tax revision and rate even if the current tax policy has since changed; this is a movement of already-paid value, not a second tax charge. A bidding product takes the entire unused net as its initial prepaid budget and requires bidMinor within the approved minimum and that budget. A fixed package must have an approved price exactly equal to the unused net; underfunded or excess-value fixed packages cannot be silently repriced. The transfer returns 202 {campaign:SocialPromotionCampaignDTO,transfer:{id,targetCampaign:SocialPromotionCampaignDTO,netMinor,vatMinor,grossMinor},refund:null,requiresApproval:false,idempotent:boolean}. The source becomes transferred and the next campaign becomes active in one database transaction; no account balance or second provider charge is created. Both retain the original Paystack payment, invoice, fee line, tax rate and provenance through later transfers or a final refund. Repeating the same operation key and next-campaign body returns the same movement. Incompatible funding returns 409 CONTENT_SOCIAL_PROMOTION_TRANSFER_AMOUNT_INCOMPATIBLE; missing paid invoice/fee custody returns 409 CONFLICT_SOCIAL_PROMOTION_TRANSFER_CUSTODY. The ordinary refund option remains available. Campaign detail returns transfer:null or {id,targetCampaignId,netMinor,vatMinor,grossMinor} for a transferred source. The campaign DTO adds transferSourceCampaignId and fundingOriginCampaignId. A later refund from a transferred campaign returns to the original Paystack payment and names the funding origin in its fiscal source; no browser instruction can choose another refund destination.

## Tracked share kits and opted-in lead broadcasts

Share kits are authorized against the current post author or property/project owner. They provide a safe public card, printable-flyer data, a QR value, WhatsApp share text and a tracked, revocable redirect; rendering the card, PDF or QR graphic remains a frontend presentation task. `SOCIAL_SHARE_PUBLIC_ORIGIN` is the public API origin for absolute tracked links and `CLIENT_URL` is the validated frontend redirect origin. No private storage URL or buyer contact is returned.

| Method/path | Request | Response |
|---|---|---|
| `POST /api/posts/share-kits` | `{targetKind:"post"|"property"|"project",targetId:<ObjectId>,operationKey:<8–100 safe chars>}` | `201 {kit:ShareKitDTO}`; exact same key/target is idempotent, changed target returns `409 CONFLICT_SOCIAL_SHARE_OPERATION` |
| `GET /api/posts/share-kits?limit=25&after=<ObjectId>` | Current author/owner profile, `limit` 1–50 | `200 {kits:[ShareKitDTO],nextCursor}`; an unavailable target is `state:"target_unavailable"` with share outputs null |
| `POST /api/posts/share-kits/:id/revoke` | No body; current owner | `200 {kit:ShareKitDTO}` with `state:"revoked"` |
| `GET /api/posts/share-kits/:token/open` | Opaque 32-character token; no authentication | `303` to the currently public target and increments open count once per request. Revoked/unavailable target returns 404; missing frontend origin returns `503 FEATURE_SOCIAL_SHARE_ORIGIN_UNCONFIGURED`. |

`ShareKitDTO` is `{id,targetKind,targetId,state:"ready"|"origin_unconfigured"|"target_unavailable"|"revoked",openPath,shareUrl,card:{title,description,imageUrl}|null,qrValue,whatsAppUrl,printable:{title,description,imageUrl,qrValue}|null,websiteEmbed:{href,title,description,imageUrl}|null,openedCount,lastOpenedAt,createdAt}`. The website embed data is a safe link/card input; the frontend renders any actual widget markup. Absolute links are null until both origins are valid. The public open route uses private/no-store and no-referrer headers.

Buyer enquiry creation (`POST /api/inquiries`) accepts optional `leadUpdatesOptIn:boolean` (default false) only for a signed-in buyer profile. Buyer enquiry DTOs include `leadUpdatesOptIn`. `PATCH /api/inquiries/:id/lead-updates-consent` with `{optIn:boolean,expectedVersion:<nonnegative integer>}` lets only the original buyer withdraw or grant consent; stale versions return `409 CONFLICT_INQUIRY_VERSION`. The seller cannot opt in a buyer. Broadcasts are in-app only and also honor the recipient's current promotions notification preference.

| Method/path | Request | Response |
|---|---|---|
| `POST /api/posts/lead-broadcasts` | `{propertyId:<owned public listing ObjectId>,title:<1–140 on-platform chars>,message:<1–500 on-platform chars>,operationKey:<8–100 safe chars>}` | `202 {broadcast:LeadBroadcastDTO}`; current seller profile with `enquiry.reply` and active resource authority |
| `GET /api/posts/lead-broadcasts?limit=25&after=<ObjectId>` | Current seller profile with `enquiry.read`; `limit` 1–50 | `200 {broadcasts:[LeadBroadcastDTO],nextCursor}` |
| `GET /api/posts/lead-broadcasts/:id` | Broadcast ObjectId; exact current owner/authorized seller profile | `200 {broadcast:LeadBroadcastDTO}` with current delivered/skipped counts |
| `POST /api/posts/lead-broadcasts/:id/cancel` | `{expectedVersion:<nonnegative integer>}` | `200 {broadcast:LeadBroadcastDTO}`; queued/processing/held only |
| `POST /api/posts/lead-broadcasts/:id/retry` | `{expectedVersion:<nonnegative integer>}` | `200 {broadcast:LeadBroadcastDTO}`; held only, rebinds current sender session and authority |

`LeadBroadcastDTO` is `{id,sellerProfileId,propertyId,title,message,state,version,scanned,delivered,skipped,lastErrorCode,createdAt,updatedAt}` with `queued|processing|completed|held|canceled`. The bounded worker stores a row cursor, recipient idempotency keys and a lease, and rechecks the sender's current session, selected profile, seat/resource authority, public listing, buyer opt-in and notification preference on each row. If a sender loses authorization the job becomes `held` without continuing; the authorized sender may retry from its persisted cursor. Recipient outcomes are deduplicated by buyer profile. A currently ineligible buyer or withdrawn consent is counted as skipped; if another current lead for that buyer becomes eligible before delivery, the same recipient can be sent once. No recipient names or contact fields appear in seller results. The scheduler uses `SOCIAL_LEAD_BROADCAST_*` and `SOCIAL_PROMOTION_CANDIDATE_LIMIT` operational settings from `firstBatchPolicies.js`.
